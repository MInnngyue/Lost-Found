# ADR-0001: 采用仓库共享记忆连接 Hermes 与 Codex

- 日期：2026-07-22
- 状态：accepted
- 适用范围：失物招领系统的智能体开发流程

## 背景

Hermes 会话可以恢复和压缩，但模型上下文有限。Hermes 派发 Codex 时使用新的临时会话，Codex 看不到 Hermes 对话、用户与其他 Codex 的对话或前一个 job。之前又要求 Hermes 把所有读取交给 Codex，导致一次简单状态核对在 Codex 完成前耗尽轮询，并被错误报告为阻塞。

## 决定

- Hermes 负责产品方向、任务边界、验收和交接，可直接做有界只读核对。
- Codex 负责代码实施、测试、实质性调试和行级审查；每个 job 均按无历史的新工人处理。
- Git、`AGENTS.md`、`PROJECT_CONTEXT.md`、`WORK_STATE.md`、相关 ADR 和任务卡组成共享长期记忆。
- 插件状态、Codex 结果和 Hermes 决定分层处理，`queued/running` 永不等同于 `BLOCKED`。
- 派发后每轮只等待一次；仍在运行就保留 job ID，并在下一用户轮次恢复同一任务。
- 同一任务最多两次实施；attempt 2 必须继承 parent job 的任务、结果和审查证据。
- 每个实施 job 只写一个 Git 仓库；跨前后端变更拆为两个关联任务，分别建立基线和验收，不扩大到共同父目录。

## 替代方案

- 复用 Codex 聊天：派发器实际使用临时会话，且隐藏上下文容易过期，未采用。
- 所有读取都派发给 Codex：延迟、成本和轮询失败已经验证，不采用。
- 让 Hermes 直接修改业务代码：会模糊项目经理与程序员的责任和验收独立性，不采用。

## 后果

- 新会话可只依赖仓库与 Git 恢复，不因某段聊天消失而中断。
- 任务信封比普通聊天提示更严格，但只在实施前生成一次。
- `WORK_STATE.md` 必须在派发后记录活动 job，并在验收后维护最终证据，否则恢复时仍需重新扫描差异。
