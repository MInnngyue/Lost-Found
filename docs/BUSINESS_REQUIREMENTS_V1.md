# 校园失物招领系统业务需求与状态流转规范 v1

## 1. 文档目的

本文档是 Lost-Found 重构的业务基线。后端实体、数据库表、管理端菜单、校园用户端页面和接口必须以本文档定义的业务规则为准。

本版本优先解决以下问题：

- 明确帖子、匹配、认领和违规处理的边界。
- 移除公开信用分，建立可解释、可审计的治理机制。
- 为审核、认领、举报、申诉和安全控制提供稳定的状态模型。
- 保证模块化单体在后续可以逐步扩展，而不依赖微服务。

## 2. 产品定位与边界

系统面向校园内部的失物招领场景，核心目标是：

1. 让用户安全发布寻物和招领信息。
2. 让管理员审核公开内容并处理违规行为。
3. 让失物方、拾得方和认领方完成可追踪的认领流程。
4. 在不暴露不必要个人信息的前提下，提供站内通知和私信。
5. 保留完整的关键业务操作记录。

系统不承担以下职责：

- 不对物品价值、真伪或所有权作司法意义上的证明。
- 不替代学校保卫处、宿管或公安机关的正式报案流程。
- 不公开用户的手机号、邮箱、学号等敏感信息。
- 不使用公开信用分对用户进行游戏化排名。

## 3. 角色模型

### 3.1 校园用户

可以：

- 注册、登录和维护个人资料。
- 发布、编辑、撤回自己的帖子。
- 浏览已审核的公开帖子。
- 发起和处理与自己有关的认领申请。
- 接收系统通知，与其他用户进行受控私信。
- 举报帖子、评论、用户或私信。
- 查看自己的举报和申诉结果。

### 3.2 内容审核员

可以：

- 审核帖子、图片和评论。
- 处理用户举报。
- 下架违规内容。
- 对用户实施临时功能限制。
- 查看与审核相关的审计记录。

### 3.3 运营管理员

可以：

- 管理分类、校区、地点和系统配置。
- 查看业务统计。
- 处理申诉。
- 处理用户限制、解封和违规案件。

### 3.4 超级管理员

可以管理角色、菜单、权限和管理员账号。

除非经过授权，管理员不应直接读取用户私信正文、密码、令牌或未脱敏联系方式。

## 4. 核心业务实体

### 4.1 帖子 `Post`

帖子表示一条寻物或招领信息。

核心属性：

- `post_type`：`LOST` 寻物、`FOUND` 招领。
- `lifecycle_status`：帖子生命周期状态。
- `review_status`：审核状态。
- 标题、描述、物品分类、颜色、校区、区域、具体地点、事件日期。
- 发布者。
- 图片。
- 创建时间、更新时间、过期时间。

`LOST` 和 `FOUND` 是类型，不是状态。

### 4.2 匹配关系 `Match`

匹配表示两个相反类型帖子之间的候选关系。

匹配结果只代表系统建议，不代表物品已经找回，也不代表认领已经成立。

### 4.3 认领申请 `Claim`

认领申请表示某个用户针对帖子发起的认领请求。

认领申请应保存：

- 申请人和帖子所有关联方。
- 申请理由或证明信息。
- 处理结果。
- 双方确认状态。
- 关键时间点。

### 4.4 举报 `Report`

举报表示用户对帖子、评论、私信或其他用户提交的风险反馈。

举报必须记录：

- 举报对象类型和对象 ID。
- 举报原因。
- 举报描述和证据。
- 处理状态。
- 处理人和处理结果。

### 4.5 违规案件 `ViolationCase`

违规案件是管理员根据举报、系统检测或人工发现创建的治理记录。

它与举报不是同一个概念：多个举报可以归并到一个案件，一个案件也可以没有用户举报。

### 4.6 申诉 `Appeal`

被限制的用户可以针对违规处理提交申诉。

申诉必须记录：

- 原处罚记录。
- 申诉理由。
- 申诉证据。
- 审核结论。
- 审核人和审核时间。

### 4.7 审计事件 `AuditEvent`

对以下行为必须记录审计事件：

- 管理员审核、下架、删除帖子。
- 管理员冻结、解封或限制用户。
- 管理员处理举报和申诉。
- 管理员修改关键业务配置。
- 用户确认认领完成。

## 5. 帖子状态机

### 5.1 生命周期状态

```text
DRAFT              草稿
PENDING_REVIEW     待审核
PUBLISHED          已发布
RESOLVED           已解决
EXPIRED            已过期
WITHDRAWN          发布者撤回
REJECTED           审核拒绝
REMOVED            管理员下架
```

### 5.2 合法流转

```text
DRAFT -> PENDING_REVIEW
PENDING_REVIEW -> PUBLISHED
PENDING_REVIEW -> REJECTED
PUBLISHED -> RESOLVED
PUBLISHED -> EXPIRED
PUBLISHED -> WITHDRAWN
PUBLISHED -> REMOVED
REJECTED -> DRAFT
```

约束：

- 只有发布者可以编辑自己的 `DRAFT`、`REJECTED` 帖子。
- 已发布帖子修改关键内容后，应重新进入审核。
- 只有 `PUBLISHED` 帖子可以出现在公开广场。
- `REMOVED`、`EXPIRED`、`WITHDRAWN` 和 `RESOLVED` 帖子不能继续发起新的认领。
- 帖子状态不再使用“已匹配”和“认领中”；这些信息由匹配和认领实体表达。

## 6. 匹配规则

### 6.1 自动匹配条件

系统只匹配：

- 类型相反的帖子。
- `lifecycle_status = PUBLISHED` 的帖子。
- 审核状态为通过的帖子。
- 尚未解决、撤回、过期或下架的帖子。
- 不属于同一用户的帖子。

### 6.2 匹配维度

初版保留以下维度：

- 物品分类。
- 颜色。
- 校区。
- 区域和具体地点。
- 遗失或拾取日期。

匹配分数仅用于排序和提醒，不用于自动认领。

### 6.3 匹配状态

```text
SUGGESTED     系统建议
VIEWED        用户已查看
CONFIRMED     用户确认相关
IGNORED       用户忽略
EXPIRED       匹配失效
```

## 7. 认领流程

### 7.1 认领状态

```text
PENDING       待帖子发布者处理
ACCEPTED      发布者接受申请
REJECTED      发布者拒绝申请
CANCELLED     申请人取消
HANDOFF       双方线下交接中
COMPLETED     双方确认完成
DISPUTED      存在争议，进入管理员处理
```

### 7.2 规则

1. 用户不能认领自己发布的帖子。
2. 同一用户对同一帖子只能存在一个有效申请。
3. 帖子发布者可以接受或拒绝申请。
4. 接受申请后，其他申请可以自动进入关闭或候补状态。
5. 双方确认交接完成后，认领状态变为 `COMPLETED`。
6. 认领争议不能由系统自动判定，应进入管理员案件流程。
7. 认领完成后，关联帖子进入 `RESOLVED`。
8. 所有状态变更必须产生通知和审计记录。

## 8. 违规治理机制

### 8.1 不使用公开信用分

系统删除用户可见的信用分、信用等级和按分数限制业务的设计。

替代机制：

```text
NORMAL        正常
RESTRICTED    部分功能受限
SUSPENDED     临时封禁
BANNED        永久封禁
```

### 8.2 处罚类型

```text
WARNING            警告
POST_RESTRICTED    限制发布
CLAIM_RESTRICTED   限制认领
MESSAGE_RESTRICTED 限制私信
CONTENT_REMOVED    内容下架
TEMP_SUSPENSION    临时封禁
PERMANENT_BAN      永久封禁
```

### 8.3 处罚原则

- 处罚必须有原因、证据、处理人和时间。
- 严重处罚必须支持申诉。
- 自动限制可以保护系统，但不能替代人工复核。
- 对新账号和高风险操作设置频率限制。
- 处罚结果不应向其他普通用户公开。

## 9. 举报与申诉

### 9.1 可举报对象

- 帖子。
- 评论。
- 私信。
- 用户。
- 认领过程。

### 9.2 举报处理状态

```text
PENDING       待处理
INVESTIGATING 调查中
RESOLVED      已处理
DISMISSED     驳回
MERGED        已合并到其他案件
```

### 9.3 申诉处理状态

```text
SUBMITTED     已提交
REVIEWING     审核中
APPROVED      申诉通过
REJECTED      申诉驳回
WITHDRAWN     用户撤回
```

## 10. 通知与私信

系统通知用于发送：

- 审核结果。
- 匹配建议。
- 认领申请。
- 认领状态变化。
- 评论提醒。
- 举报和申诉处理结果。

私信必须具备：

- 会话和消息权限校验。
- 发送频率限制。
- 举报和禁言能力。
- 敏感内容审计能力。
- 删除或隐藏消息的策略。

## 11. 安全验收边界

### 11.1 应用安全

- 使用 Spring Security 进行认证和授权。
- 使用方法级权限保护业务资源。
- 对每个资源执行对象级权限校验。
- 登录、注册、上传、发布、评论、私信和举报接口限流。
- 对输入长度、格式、枚举值和文件类型进行校验。
- 使用 MyBatis 参数绑定，禁止把用户输入拼接进 SQL。
- 动态排序字段必须使用白名单。

### 11.2 基础设施安全

- 生产环境通过 WAF、反向代理或网关承接公网流量。
- 源站不直接暴露公网。
- MySQL、Redis 不暴露到公网。
- 应用使用最小权限数据库账号。
- 密钥、数据库密码和 JWT 密钥不能提交到 Git。
- 日志不得记录密码、令牌和完整私信内容。

### 11.3 文件与内容安全

- 限制上传文件大小、数量和扩展名。
- 检查真实 MIME 类型。
- 上传文件重命名并与代码目录隔离。
- 图片和文本内容进入审核流程。
- 输出用户内容时进行 XSS 防护。

## 12. MVP 范围

第一阶段必须完成：

1. 用户登录和权限。
2. 帖子发布、审核、展示、编辑、撤回和过期。
3. 图片上传和访问控制。
4. 认领申请、接受、拒绝、取消和完成。
5. 系统通知。
6. 举报和违规处理。
7. 管理员审计。
8. 对象级权限、输入校验和接口限流。

第二阶段实现：

1. 自动匹配。
2. 私信。
3. 评论和回复。
4. 申诉。
5. 数据统计。

第三阶段考虑：

1. 校园统一身份认证。
2. 内容审核服务。
3. 更精细的反滥用规则。
4. 多校区或多学校租户能力。

## 13. 迁移规则

迁移时不直接照搬旧表和旧状态：

1. 先按本文档建立新的状态枚举。
2. 再设计 `lf_post`、`lf_match`、`lf_claim`、`lf_report`、`lf_violation_case`、`lf_appeal` 和 `lf_audit_event`。
3. 对旧数据进行状态映射。
4. 后端先完成帖子审核闭环。
5. 再完成认领闭环。
6. 最后迁移匹配、评论、私信和统计。

任何状态流转、处罚规则或权限规则发生变化，都应先更新本文档和对应测试，再修改实现。
